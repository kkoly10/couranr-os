## 3. Implementation contract

**File:** rewrite `app/(couranr)/business/customers/page.tsx`. One page, two states switched on `?customer=` (server component reading `searchParams`, or client + `useSearchParams` matching sibling patterns). New API under `app/api/couranr/merchant/customers/` (or extend `lib/couranr/requests/commands.ts` with a derivation query) — service-role client, per-query tenant scoping, actor resolved via `resolveRequestActor`.

**Slice A — ship now, zero new schema (derived read-only book):** customers list = server-side aggregation over `couranr_delivery_requests` grouped by normalized recipient identity (lowercased email → digits-only phone → exact name fallback) within `business_account_id`. Real data only: recipient name, delivery count, last-delivery date, last payer_type, distinct dropoff addresses. This satisfies: Empty state (real — no requests → "No customers yet" + CTA to `/business/deliveries/new`; never fabricate a number), Active, Duplicate warning (two identity keys sharing a normalized phone/email), and MER-009's No-deliveries-is-impossible caveat, Active delivery (any request in non-terminal `request_state`), Conflicting address (same identity, ≥2 distinct dropoff snapshots — surface both, newest labeled). **Archived (MER-008) and Archived + standalone no-deliveries customer (MER-009) are NOT reachable without Slice B — render the states' UI behind data that cannot yet produce them and say so in the ledger, do not fake a toggle that writes nowhere.**
- Detail sections (MER-009): identity header (name, masked contact with reveal affordance); addresses (from snapshots; conflicting-address banner); delivery history (list of that identity's requests, linking to `/business/deliveries/[id]`); payer preference (display last-used + PAY-001 note that both options remain available — no editable stored preference until Slice B); Repeat delivery button → `/business/deliveries/new` prefilled (client-side prefill or draft-create POST with fresh idempotency key); Message → link into the delivery's conversation (delivery context only, TRM-002 roles).
- **Edit contact/address and Create customer are disabled in Slice A** (no table to write). Show as visible-but-disabled with "coming with customer records" copy rather than omitted, since the registry lists them as allowed actions.

**Slice B — net-new, requires reviewed migration:** additive migration creating `public.merchant_customers` (id, business_account_id FK restrict, created_by, display_name, email, phone, normalized_email, normalized_phone, payer_preference `merchant|customer|null`, notes text NULL, archived_at timestamptz NULL, version int, idempotency uniq per business) and `public.customer_addresses` (customer FK, address jsonb object-checked, label, instructions, archived_at). Copy the established posture verbatim from `20260731045417`: RLS enabled + zero policies (deny-all), revoke PUBLIC/anon/authenticated, service_role only, hard-guard `to_regclass` abort instead of `if not exists` on a possibly-different shape, `version` + idempotency per spec §14 concurrency. Archive = `archived_at` stamp, never DELETE (append-only convention; production service_role has no DELETE). Backfill/link: nullable `merchant_customer_id` on new *drafts* only — never mutate submitted requests' snapshots (they are documented as immutable, migration `:101-103`).

**PII projection rules (binding):**
- List view: name, delivery count, last activity, duplicate/archived badges only. **No full street address, no unmasked phone/email** — mask (`k•••@…`, `(…) …-1234`) per `UI_SCREEN_REGISTRY.md:351`. Payment credentials cannot appear: none are stored outside Stripe/`private` schema — keep it that way.
- Detail view: full contact/address allowed (merchant already owns this data — it came from their own requests), but internal/ops notes never (pattern at `commands.ts:818-837`).
- Analytics/logs: never copy addresses, phones, gate codes (spec §17); log customer IDs, not identities.
- Copy: "your customers", "Couranr Support" — never language implying Couranr owns the relationship (MKT-002, `UI_SCREEN_REGISTRY.md:362`).

**Role/tenant boundaries:**
- Tenant: every query `eq("business_account_id", …)` with membership re-checked server-side per request (business-accounts route pattern); cross-tenant read must be impossible even via `?customer=` ID guessing — resolve the customer *within* the caller's business, 404 otherwise.
- Roles — **open decision, do not invent**: no registry record defines customer-record permissions (TRM-002 is conversations-only by its own text; DRP-001 is request create/submit/read/review only). Safe bounded behavior: **read = any active member** (citing DRP-001's read rule, the only decided read precedent), **Slice-B writes (create/edit/archive/notes) = owner|manager|dispatcher** as a *bounded proposal that must be recorded in the registry before MER-008's edit actions ship* — cite the new record, not DRP-001-by-analogy (the registry explicitly withdrew analogy reasoning at TRM-002 `supersedes_analogy`). Viewer/billing: read list, no writes; the Message action additionally hidden from viewer/billing (that one IS decided — TRM-002). Invited/disabled/anonymous: denied everything.
- "Repeat delivery" button: owner|manager|dispatcher only (it creates a request — DRP-001, decided).

**Gating open decisions:** customer-record role matrix (above); archived semantics/who may archive; whether stored payer_preference may pre-select payer on repeat delivery (PAY-001 says onboarding captures *a default only* — safe: preselect but always show both options); duplicate-merge (not in allowed actions — show warning only, no merge).
