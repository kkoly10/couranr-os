## 2. MER-004 — Deliveries list `/business/deliveries` (the deep contract)

Registry row: `UI_SCREEN_REGISTRY.md:299-308`. Purpose: find/manage requests across request, payment, readiness, review, and fulfillment states. Allowed actions: Filter; search; create; open; duplicate; cancel when allowed; mark ready. Required states: all canonical combinations; empty; error. Constraint (`:307`): "Never collapse independent state groups into one misleading status."

**Current state: placeholder only** — `app/(couranr)/business/deliveries/page.tsx` renders `ScreenPlaceholder screenId="MER-004"`. Nothing is fetched. Everything below is what it CAN already call vs net-new.

### Already-real backend it can call today
- **List**: `GET /api/couranr/delivery-requests?businessAccountId=<uuid>` (`app/api/couranr/delivery-requests/route.ts:64-77`) → `listDeliveryRequests` (`lib/couranr/requests/commands.ts:914`): newest-first, limit 50 (max 200), permission `read` (any active member of the right business, `lib/couranr/requests/permissions.ts:87`), returns `toDeliveryRequestView` allow-list rows (`lib/couranr/requests/view.ts:20-63`) carrying `requestState`, `readinessState`, `reviewState`, `serviceAreaReviewState`, `payerType`, recipient, quote. **Currently zero consumers** — the only `client.ts` reference to that path is the POST (`components/couranr/requests/client.ts:110`); no `fetchDeliveryRequests` helper exists (verified grep).
- **Workspace scope**: `GET /api/couranr/me/business-accounts` via `fetchMyBusinessAccounts()` (`client.ts:176`).
- **Mark ready**: `POST /api/couranr/delivery-requests/[id]/readiness` (`.../readiness/route.ts:20-59`) — destination-named, version-checked (`expectedVersion`), maps to the four SQL readiness commands (`REQUEST_COMMANDS`, `lib/couranr/requests/states.ts:64-77`; `READINESS_TRANSITIONS:255`). UI exists as `MerchantReadinessPanel` (used by MER-007) — reuse per-row or link to detail.
- **Per-request lifecycle facets**: `GET /api/couranr/delivery-requests/[id]/fulfillment` (`.../fulfillment/route.ts:24-92`) returns `{requestState, readinessState, payment{paymentState,…}, servicePlan{planState,…}, delivery{fulfillmentState,…, driverAssigned}}` — per-id only; **no list-level join exists**. Derived stage: `lifecycleStage()` + `LIFECYCLE_STAGE_LABELS/TONE` (`lib/couranr/fulfillment/lifecycle.ts:15-58,93,144-…`).
- Vocabularies to render as SEPARATE badges (STA-001): request labels `REQUEST_STATE_LABELS` (`view.ts:126-136`); payment `PAYMENT_STATES` + `REACHABLE_PAYMENT_STATES` (`lib/couranr/payments/states.ts:7,42`); readiness/review from `requests/states.ts:30-46`; fulfillment vocabulary in `couranr_deliveries` (STA-002).

### Net-new work for MER-004
1. **Client list helper + page component** (`fetchDeliveryRequests` in `components/couranr/requests/client.ts`; a `DeliveriesList` client component replacing the placeholder). Sections: workspace selector (multi-membership), facet filter bar (one filter group PER state group — request, payment, readiness, fulfillment — never a merged "status" dropdown, STA-001 + registry `:307`), search box, table (recipient, created, request-state badge, readiness badge, payment badge where known, quote subtotal via `formatCents`, open → `/business/deliveries/[id]`), Create button → `/business/deliveries/new`, empty state ("No deliveries yet" + create action — never fabricated counts, MER-001 constraint `UI_SCREEN_REGISTRY.md:274` extends: real posted data only), error state (surface `ApiFailure.correlationId` via `withReference`, `client.ts:261`).
2. **Payment/fulfillment facets on the LIST**: server-side. Options: (a) N+1 per-row `GET .../fulfillment` (works today, slow, fine for ≤50 rows first slice); (b) extend the list route/command to join `couranr_payment_obligations` + `couranr_deliveries` per business (new command, review required). Do NOT invent a client-side merged status.
3. **Search/filter**: `listDeliveryRequests` has no search parameter (`commands.ts:914-940`) — either client-side filter over the ≤200 fetched rows (safe first slice) or a reviewed command extension (`ilike` on recipient_name is the obvious server form).
4. **Cancel**: **NO cancel command exists.** `cancelled`/`closed` are deliberately unreachable — "they belong to the payment and fulfillment slices, which are not built yet" (`lib/couranr/requests/states.ts:119-127` comment); `cancel` absent from `REQUEST_COMMANDS:64-77`. Safe behavior until the command lands: show "Cancel — contact Couranr Support" (or hide) for post-authorization rows; a first-slice merchant self-cancel would only be defensible for `draft`/pre-authorization rows ($0 per CAN-001) and MUST be a new named SQL command with audit event, reviewed migration — do not patch `request_state`.
5. **Duplicate**: net-new; safe form is client-side prefill of `/business/deliveries/new` from an existing view row (no new backend). No spec text forbids it; AI/pricing constraints don't apply since the draft re-prices server-side (`POST` recomputes; `route.ts:46-53`).
6. **Mark ready inline**: gate on `readinessState` transitions (`canChangeReadiness`, `states.ts:275`) and pass `expectedVersion`; on `conflict` failure re-fetch.

### Role/tenant boundaries
- Read (list, open): any ACTIVE member of that business, all five roles (`permissions.ts:87` — "Every active member of the right business may read"); operations may read cross-business, cannot write (`:64-70`).
- Create/submit (and readiness, which routes through actor→command capability): owner|manager|dispatcher only (`WRITE_ROLES`, `permissions.ts:41`; viewer/billing get `role_may_not_write`).
- TRM-002 governs CONVERSATIONS only (`scope` field, registry `:2146`) — do not import its read-refusal into the deliveries list; the list itself is readable by viewer/billing.
- Tenant scope: `businessAccountId` is caller-supplied but every command re-checks membership (`canActOnDeliveryRequest`, `permissions.ts:54-96`); the UI must still never offer a business the caller isn't a member of (source the selector from `/api/couranr/me/business-accounts`).
