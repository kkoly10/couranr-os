## 4. Roles and tenant boundaries

- Tenancy: server-resolved membership only; every route re-checks (`me/business-accounts/route.ts:15-18`; `resolveRequestActor` on the list route `delivery-requests/route.ts:70-71`). The dashboard must pass an explicit `businessAccountId` picked from the caller's own memberships; multi-membership users need an account switcher (pattern already in `NewDeliveryFlow`).
- Request create/submit: `owner|manager|dispatcher` only — DRP-001, `lib/couranr/requests/permissions.ts:41` (`WRITE_ROLES`); read: any active member (`:88`). So the "Create delivery" and "Mark ready" actions must hide/disable for `viewer|billing` — enforcement already exists server-side; the dashboard mirrors it for UX.
- Conversations tile: TRM-002 (`02_DECISION_REGISTRY.json:2146-2225`) — `viewer` and `billing` are refused **read**, not just send; `listConversations` already enforces it, so for those roles the tile shows the refusal/empty state, never thread subjects. Cite TRM-002, never DRP-001, in any new code (`:2219`).
- TRM-002's scope is "conversations and messaging only" (`:2179`); the full role matrix beyond requests+messaging **remains unresolved** (`:2421`) — a gating open decision. Safe behavior: dashboard adds NO new permission decisions; it only renders what existing routes already allow/deny.
